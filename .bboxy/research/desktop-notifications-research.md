# Desktop notifications: use versus build

Researched 2026-10-23 by a read-only research subagent under the Architect's brief, nothing built. Format: `source — fact`; `unverified` marks claims not confirmed from a primary source; `@main` is an unpinned branch read that day. The design this evaluates is [[desktop-notifications]]; the decision is [[d45-desktop-notifications|#45]]. ## 1. Apple — UserNotifications facts (primary)
- Apple docs `current()` — "Always use this method to retrieve the shared notification center object for your app"; macOS 10.14+, iOS/iPadOS 10+, Mac Catalyst 13.1+, visionOS 1.0+; page says nothing about bundles (https://developer.apple.com/documentation/usernotifications/unusernotificationcenter/current())
- Apple docs `requestAuthorization(options:completionHandler:)` — "The first time your app calls the method, the system prompts the person… Subsequent calls to this method don't prompt the person again"; "Always call this method before scheduling any local notifications" (https://developer.apple.com/documentation/usernotifications/unusernotificationcenter/requestauthorization(options:completionhandler:))
- Apple docs "Asking permission" — `.provisional` "automatically grants authorization" without a prompt, status stays provisional until the user keeps/turns off; always check `getNotificationSettings` before scheduling (https://developer.apple.com/documentation/usernotifications/asking-permission-to-use-notifications)
- Apple docs `UNNotificationRequest.identifier` — "If you use the same identifier when scheduling a new notification, the system removes the previously scheduled notification with that identifier and replaces it with the new one" (https://developer.apple.com/documentation/usernotifications/unnotificationrequest/identifier)
- Same page — replacement of an already-*delivered* notification by re-using its identifier is not stated; `unverified` from Apple docs (crates below rely on it in practice)
- Apple docs `removeDeliveredNotifications(withIdentifiers:)` — removes matching notifications from Notification Center asynchronously on a background thread; identifiers not currently displayed are ignored (https://developer.apple.com/documentation/usernotifications/unusernotificationcenter/removedeliverednotifications(withidentifiers:))
- Apple docs `delegate` — `weak var delegate`; "To guarantee that your app responds to all actionable notifications, you must set the value of this property before your app finishes launching" (https://developer.apple.com/documentation/usernotifications/unusernotificationcenter/delegate)
- Apple docs `userNotificationCenter(_:didReceive:withCompletionHandler:)` — response carries `actionIdentifier`; "you must execute this block"; "If you do not implement this method, your app never responds to custom actions" (https://developer.apple.com/documentation/usernotifications/unusernotificationcenterdelegate/usernotificationcenter(_:didreceive:withcompletionhandler:))
- Apple docs "Handling notifications and notification-related actions" — "When the user selects an action, the system launches your app in the background and calls the delegate's userNotificationCenter(_:didReceive:withCompletionHandler:) method" (launch-and-deliver) (https://developer.apple.com/documentation/usernotifications/handling-notifications-and-notification-related-actions)
- Apple docs `UNNotificationDefaultActionIdentifier` — "indicates the user opened the app from the notification interface"; needs no category configuration; delivered via `didReceive` (https://developer.apple.com/documentation/usernotifications/unnotificationdefaultactionidentifier)
- Apple docs `NSUserNotificationCenter` — introduced macOS 10.8, deprecatedAt 11.0, "All NSUserNotifications API should be replaced with UserNotifications.frameworks API" (https://developer.apple.com/documentation/foundation/nsusernotificationcenter)
- Apple Developer Forums thread 679326 (forum, not docs) — un-bundled LaunchAgent calling `currentNotificationCenter`: "*** Assertion failure in +[UNUserNotificationCenter currentNotificationCenter] … bundleProxyForCurrentProcess is nil: mainBundle.bundleURL file:///…/Debug/"; no Apple-staff answer (https://developer.apple.com/forums/thread/679326)
- Apple Developer Forums thread 724249 (forum) — CLI binary: "uncaught exception 'NSInternalInconsistencyException', reason: 'bundleProxyForCurrentProcess is nil…'" (https://developer.apple.com/forums/thread/724249)
- Bundle requirement in Apple *documentation* — not found on any fetched page; `unverified` as doc; confirmed only by the two forum crashes and by three crates guarding on `NSBundle.mainBundle.bundleIdentifier` (sections 6, 7, 8)
- "Ad-hoc signature is sufficient" — claimed by mac-usernotifications docs (section 6), absent from Apple docs; `unverified`

## 2. Microsoft — toast facts (primary)
- Learn `ToastNotification.Tag` — "unique identifier of this notification within the notification Group"; max 16 chars, 64 since build 15063; exception on null/empty (https://learn.microsoft.com/en-us/uwp/api/windows.ui.notifications.toastnotification.tag)
- Learn `ToastNotificationHistory.Remove` — overloads Remove(tag), Remove(tag, group), Remove(tag, group, applicationId) (https://learn.microsoft.com/en-us/uwp/api/windows.ui.notifications.toastnotificationhistory.remove)
- Learn Windows App SDK "Remove and manage app notifications" — Tag "identifies a specific notification", Group "a set"; RemoveByTagAsync / RemoveByGroupAsync / RemoveByTagAndGroupAsync / RemoveByIdAsync / RemoveAllAsync (commit 3ee99c3) (https://learn.microsoft.com/en-us/windows/apps/develop/notifications/app-notifications/manage-app-notifications)
- Learn archived hh802762 — "Without a valid shortcut installed in the Start screen or in All Programs, you cannot raise a toast notification from a desktop app"; shortcut carries `System.AppUserModel.ID` (https://learn.microsoft.com/en-us/previous-versions/windows/desktop/legacy/hh802762(v=vs.85))
- Learn archived "Respond to toast activations" — Win32 apps need Start shortcut with `System.AppUserModel.ID` + `System.AppUserModel.ToastActivatorCLSID`; COM server implementing `INotificationActivationCallback` registered at `HKCU\SOFTWARE\Classes\CLSID\{CLSID}\LocalServer32`; "If your app is not running, it will be launched by your local COM service" (https://learn.microsoft.com/en-us/previous-versions/windows/desktop/win32_tile_badge_notif/respond-to-toast-activations)
- Learn Windows App SDK console article (commit f1417ed) — "For unpackaged apps, Register() automatically sets up the COM server registration… You don't need to configure COM activation or an AUMID manually"; needs Microsoft.WindowsAppSDK runtime; app must stay running or the click "will cold-launch a new process" (https://learn.microsoft.com/en-us/windows/apps/develop/notifications/app-notifications/app-notifications-console)
- Learn Windows App SDK quickstart (commit 6f2c245) — "When the app is not running, Windows launches the app via COM activation and the activation kind is reported as Launch"; arguments arrive via `NotificationInvoked`; elevated apps unsupported (https://learn.microsoft.com/en-us/windows/apps/develop/notifications/app-notifications/app-notifications-quickstart)
- Classic en-us pages `toast-desktop-apps` and `send-local-toast-desktop-cpp-wrl` — both return HTTP 404 today under /windows/apps/design/… and /windows/apps/develop/…; current location `unverified`

## 3. freedesktop — Desktop Notifications spec (primary)
- Spec title page — "Desktop Notifications Specification", Version 1.3, Publication Date 18 August 2024 (https://specifications.freedesktop.org/notification/latest/)
- protocol.html `Notify` — `UINT32 Notify(STRING app_name, UINT32 replaces_id, STRING app_icon, STRING summary, STRING body, as actions, a{sv} hints, INT32 expire_timeout)`; replaces_id: "The server must atomically (ie with no flicker…) replace the given notification with this one"; 0 = no replace; return equals replaces_id when non-zero (https://specifications.freedesktop.org/notification/latest/protocol.html)
- protocol.html `CloseNotification(UINT32 id)` — "forcefully closed and removed from the user's view"; emits NotificationClosed; empty D-Bus error if id unknown (same URL)
- protocol.html `ActionInvoked(UINT32 id, STRING action_key)` — emitted on click of the notification itself or an action button; "clients should not assume servers will generate this signal" (same URL)
- protocol.html `NotificationClosed(UINT32 id, UINT32 reason)` — 1 expired, 2 dismissed by user, 3 CloseNotification, 4 undefined/reserved (same URL)
- protocol.html `ActivationToken(UINT32 id, STRING activation_token)` — may precede ActionInvoked; X11 startup id or Wayland xdg-activation token for raising a toplevel (same URL)
- basic-design.html — "The default action (usually invoked by clicking the notification) should have a key named "default""; actions are [key, label, …] pairs; capabilities `actions`, `persistence`, `action-icons` via GetCapabilities (https://specifications.freedesktop.org/notification/latest/basic-design.html)

## Judgement (not evidence)
- No existing crate meets all four requirements on macOS with the app owning click routing. notify-rust's `preview-macos-un` path is the only one with stable-id replace + close + default-click; it is a preview feature, blocking-handle API, and the delegate belongs to mac-usernotifications, so winit's AppKit lifecycle cannot hook it. user-notify has the right shape (delegate, remove-by-id, permission) but generates UUID identifiers (no replace), is LGPL-3.0, drags tokio onto every target, and its Windows click path is protocol activation only. usernotifications-rs is a day-old 0.4.2 on bespoke FFI, two stars.
- Build. Facade + `-macos` over objc2-user-notifications 0.3 directly: `define_class!` delegate (par-term's file is a 1:1 template), `setDelegate` + leak before the winit event loop runs, `requestAuthorization(Alert|Sound)`, `UNNotificationRequest` identifier = our stable id, `removeDeliveredNotificationsWithIdentifiers`, osascript fallback when `mainBundle.bundleIdentifier` is nil [Architect: rejected, `AGENTS.md` bans desktop scripting; an unbundled run posts nothing, decision [[d44-waiting-attention|#44]]]. Roughly 300 lines, one Objective-C-free dependency chain, same objc2 family winit already links.
- Verify two Apple behaviours on this machine before trusting them, since neither is in Apple docs: (a) ad-hoc-signed `.app` with Info.plist is enough for `currentNotificationCenter()` and delivery; (b) re-adding a request with a delivered notification's identifier replaces it in Notification Center rather than only the pending one.
- Cold-launch click delivery depends on the delegate being set "before your app finishes launching"; with winit that is before `EventLoop::run` — write the test, don't assume.
- Windows dummy now. When real: in-process clicks via tauri-winrt-notification 0.8 cost nothing but show as PowerShell until an AUMID shortcut exists; launch-on-click needs the shortcut + `ToastActivatorCLSID` + `LocalServer32` COM server (archived docs) or the Windows App SDK runtime (not Rust-native). Decide then, not now.
- Linux dummy now. When real: zbus directly against spec 1.3 (replaces_id, CloseNotification, ActionInvoked "default", ActivationToken for Wayland focus); current zbus is 6.1, notify-rust still pins 5.
- Android later means JNI into NotificationManager, no shortcut; wasm later means Service Worker `notificationclick` for routing, `tag` for replace. The facade's id/replace/remove/click shape maps onto all of them.
- Names are free; publish `bboxy450-desktop-notifications` and `-macos` first, keep `-windows`/`-linux` as stubs that return `Unsupported`.
